# Changelog

## [Unreleased]

### Added

- Initial release: `Scry.Engine.InfluxDB` -- a real `Scry.Core.EngineBehaviour` implementation over InfluxDB 1.x, via `req` rather than `instream` (confirmed stale -- last Hex release April 2023, no InfluxDB 3.x support -- *and* architecturally disqualified: a compile-time `use Instream.Connection` macro-based module defined in the consuming application, the identical shape that already ruled out `snap` for `scry_engine_elasticsearch`). The `time-series` kind's *fourth* real backend, after `scry_engine_ch`/`scry_engine_redistimeseries`/`scry_engine_loki`, and the first with a genuinely SQL-like native query language (InfluxQL) to translate `WHERE` into for real. `scry_time_series`'s own `LAST`-lowering pass already rewrites into an ordinary `WHERE` predicate before any engine sees the query -- the identical "zero time-series-specific code needed" finding established three times over already -- so this package's own real work is `Scry.Engine.InfluxDB.WhereTranslator`.
  **`source` maps onto one InfluxDB measurement, inside one fixed database** (`database` set at `Conn.open/1` time), the same relationship a SQL table has to its own schema. Every row exposes InfluxDB's own real column set: `"time"` (a real `DateTime.t()`, decoded from the server's own `epoch=ns` form) plus every tag and field, flattened together with no distinction at query time.
  **A real, bind-parameterized `WHERE` translator -- a deliberately different posture from this family's other time-series adapters**: InfluxQL has real `WHERE`/bound-parameter support (confirmed directly, `$name` placeholders plus a `params` JSON argument, not manual string interpolation), unlike a bare `TS.RANGE` range primitive or a LogQL selector with no boolean predicate language -- so `WhereTranslator` mirrors the full-`WHERE`-translation posture `scry_engine_duckdbex`/`scry_engine_ch`/`scry_engine_myxql` already have for real SQL, rather than the narrower extraction-only posture the other time-series adapters use. `{:cmp, ...}` leaves combine via `AND`/`OR`, plus `NOT` of a plain equality/inequality; anything else declines outright.
  **`ORDER BY`/`LIMIT`/`OFFSET` push down only when InfluxQL itself can express them**: confirmed directly, InfluxQL's own `ORDER BY` accepts only `time` (`ORDER BY value DESC` is a real, clean parse error) -- pushed down together only when `order_bys` is empty or exactly one key on `"time"`, the identical "narrower but always correct" choice `scry_engine_redistimeseries` already makes. When pushed, `order_bys`/`limit`/`offset` are cleared from the query handed to `Scry.Core.QueryOps.run_flat/3` afterward -- the same real, confirmed `scry_engine_elasticsearch` double-application finding applies here too. `WHERE` is never cleared, even when fully pushed down, since re-checking an already-satisfied predicate is a safe no-op.
  `GROUP BY`/aggregates are never pushed to InfluxQL's own -- the identical "no time-bucketing construct in the language yet" gap already documented for `scry_engine_redistimeseries`/the corrected `scry_engine_timescaledb` entry, which also sidesteps InfluxQL's own confirmed multi-series-per-tag-group result shape under a native `GROUP BY`.
